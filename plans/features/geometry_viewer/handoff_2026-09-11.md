## Part 1: Increment 6, the port

The plan's Increment 6 entry is the specification.  The order of work:

1. **One source of truth for the point projection.**  `GeometryScene.detector_coordinates`
   holds a copy of the projector's per-geometry formulas, pinned by the
   corner-projection test.  mbirtorch has no public method that maps object points to
   detector indices; its mapping lives in private per-view helpers written for the
   projector (`_cone_pixel_xy_mag`, `_parallel_hfan_math`, the multiaxis helpers, and
   `ConeBeamModel.detector_mn_to_uv`).  Add `project_points(points_xyz, view_index)` to
   `TomographyModel`, implemented in each model class from the same helpers the
   projector uses, which means separating each helper's pixel-index-to-position step
   from its position-to-detector step.  Test it the way the prototype tests the scene.
   The first check is against the centroids of `sparse_forward_project` footprints of
   single voxels, within half a detector pixel, for the six geometries of
   `gv1_conventions_probe.py`.  The second is against the prototype's
   `GeometryScene.project_points`, to a tight tolerance.
2. **The first design question, for Greg.**  The web page cannot import torch, so it
   needs the numpy formulas the ported scene would drop.  One choice is a scene with
   both routes: `model.project_points` when it is built from a model, and its own
   formulas when it is built from a parameter dictionary, with the formulas pinned by
   the test above, so that one file serves the package and the page.  The other choice
   is a separate numpy scene for the page.  Put the choice to Greg before moving files.
3. **Move the scene and the viewer** into the package following the slice viewer's
   pattern (`mbirtorch/viewer.py` with its thin wrapper in `mbirtorch/view_utils.py`).
   Expose `mbirtorch.geometry_viewer(model, ...)` beside `mbirtorch.slice_viewer`, with
   the same nonblocking registry behavior; the prototype's `geometry_viewer` function
   already has that shape.  Keep the `AXLIM_CLIP` guard, because mbirtorch requires
   matplotlib with no version bound.
4. **Move the tests**, add a demo, a docs page under `docs/source/`, and a row in
   `plans/API_specification.md` under "Viewing".
5. **Fix the two docstrings** named in the conventions record: the `TranslationModel`
   sign of a positive z translation, and the `MultiAxisParallelModel` definition of the
   elevation.
6. **Keep the page honest.**  `geometry_defaults.py` and its test against the real
   models stay as they are, and the build script goes on copying the page's modules from
   their sources; `test_web_app.py` checks the copies.  When the port changes what the
   page copies, rebuild the page, verify it in a browser, and hand the three files of
   `web/lite/` to Greg for the Space.

## Part 2: small items, if there is time

- The phantom's projected outline on the detector face is not cut at the detector's
  edge, unlike the volume box's outline; Greg has not asked for it to be.
- Seven label collisions remain in the top and side views at views the overlap test
  does not measure; `gv6_review_items_findings.md` lists them.  Greg's decision is that
  a label clear in most views need not be clear in every view, so this is not a task
  unless a figure for a record shows one of them.

Decisions already made, not to be reopened without Greg: matplotlib is the frontend;
the object frame stays right-handed with +z along the slice index and the drawing puts
-z at the top; the multiaxis source is on the +y side; the entry point is the function
`geometry_viewer`, not a model method; the region of reconstruction is the mask's own
ellipse, through the centers of the outermost voxels; the fit statement is two rows,
lateral and axial; the web page's sinograms are the projector's, computed at build time
at 8 bits for each geometry's default scan; PNG figures are not tracked in
`mbirtorch_plans`, except the Space tile and the logo copy under `web/`.

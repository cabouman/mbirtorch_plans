2. Software Architecture

This blueprint says which objects compute the time-resolved reconstruction, what each object does, and which object holds each quantity. It extends the MACE4D code in mbirtorch.

1. Objects

The user holds one object, the time-resolved model. It owns one CT model for each interval between frame times, and it owns one motion object. For each run, it builds one MACE object with the five agents of the Theory blueprint. After each outer pass, it asks the motion object for a new d and replaces the two temporal agents with new ones that use it. The names on this page are working names, and the User API blueprint settles the public names.

2. Existing code that the design depends on

  • MACE in mace.py holds one input array for each agent, the consensus average, an accumulator for the next average, and the sum that updates the inputs. With five agents, these are eight full 4D arrays. They are on the device of the initial array, which MACE4DModel puts on the host. An agent may split its work into tasks, and each task has a region of the array and may name a device. MACE folds in an agent's output only in the regions that its tasks return.
  • ForwardProxAgent calls TomographyModel.prox_map, which runs VCD on one volume. It configures its model on one device. Each VCD subset update does one sparse back projection and one or two sparse forward projections.
  • TomographyModel.vcd_partition_iterator passes the recon to the subset updater without reading it. A subset updater for two frames can therefore use it unchanged.
  • HyperplaneAgent denoises stacks of 3D volumes taken from the 4D array. It accepts only the spatial axes 1, 2, and 3.
  • construct_time_frame_models in utilities.py builds one CT model for each MACE4D frame. It assumes that the views are in time order and that the angle changes at a constant rate. It drops the views at the end of the scan that cannot fill a whole frame.

3. The time-resolved model

MethodWhat it does
TimeResolvedModel(ct_model, labels, part_kinds, frames_per_rotation)It builds one CT model for each interval, the frame times, the hat weights of each view, and the motion object. It reads V from the angle step of ct_model. This version uses τj=j, with the views in time order at a constant angle step.
set_params(**kwargs)It sets the MACE, prior, and outer-loop parameters. These include σy, σp, the temporal weight bt, its starting fraction, the number of passes over which it rises, the tolerance ε, the maximum number N of outer passes, and the iteration counts of the temporal tasks and of the registration.
set_device_pool(devices) and devicesThey set and report the devices, as in MACE4DModel.
recon(sinogram, weights, start_recon, start_model, ...)It runs the outer loop and returns the frames, d, and a dict of run information. start_recon is the MACE4D reconstruction, and start_model is the MACE4DModel that made it.

Step size. The time-resolved model sets one σy from the full sinogram, unless set_params gives it, and one σp. It turns off the automatic regularization of every interval model, and it passes σp to every agent. As a result, the five agents are proximal maps with one step size, as the Theory blueprint requires. The 3D denoiser uses the spatial neighbor weights of ct_model.

Starting point. The time of a MACE4D frame is the center of its view window in start_model.view_slices. recon checks that the MACE4D frames cover the whole scan. It interpolates start_recon linearly to the frame times tk to get the starting frames. The motion object computes the starting d. It registers each moving part of each MACE4D frame to MACE4D frame 0, and it starts each search from the result for the previous MACE4D frame. It then interpolates the result to the frame times.

Outer loop. Each outer pass runs MACE at the current d. The motion object then registers frames 1 to K−1, and frame 0 keeps d=0. The weight bt rises linearly to its final value over the number of passes that set_params sets. Once it has reached that value, recon stops when no translation has changed by more than ε in Euclidean length, or after N passes. It then returns the frames of the last pass and the d that pass used. Otherwise it stores the new d, replaces the two temporal agents, and starts the next pass.

MACE folds in only the regions that an agent's tasks return. Each data-fit agent and each temporal agent therefore adds one task that returns its input unchanged for the frames that its intervals or pairs do not cover. These frames are frame 0 for the odd agents, and frame K−1 for the even agents when K is odd. Each agent checks that its tasks cover every frame exactly once. The data-fit agents keep their warm starts across outer passes, because their proximal maps do not depend on d.

5. The two-frame data-fit proximal map

The two-frame proximal map is the interval form of the data-fit proximal map that MACE4D uses now. In MACE4D, the data-fit agent of each frame is a ForwardProxAgent, which calls TomographyModel.prox_map on the model of that frame. The MACE input of frame t is vt, and 𝒲t is the set of views in its angular window. All of these views are compared with one volume.

x^t= argminx { 12σy2 ∑j∈𝒲t ‖yj−Ajx‖Λj2 + 12σp2 ‖x−vt‖2 }

The new data-fit agents solve the same problem for the set ℐi of views in interval i, with two frames as the unknowns. Each view is compared with the hat-weighted average of the two frames, where λj=φi+1(τj).

(x^i,x^i+1)=argminxi,xi+1 12σy2∑j∈ℐi‖yj−Aj((1−λj)xi+λjxi+1)‖Λj2 +12σp2(‖xi−vi‖2+‖xi+1−vi+1‖2)

The two proximal maps are related in four ways.

  • Both are the data-fit agents of a MACE loop. The inputs vi and vi+1 are two frames of the agent's MACE input, and σp is the same sigma_prox parameter.
  • If every λj is 0, the two-frame problem splits in two. Then x^i+1=vi+1, and x^i is the result of prox_map on the views of the interval.
  • Both use VCD with the same projectors and partitions. Each two-frame subset update does two back projections and two forward projections, with the hat weights applied to the views. With the positivity constraint, it may do four forward projections, just as a subset update of prox_map may do two. Its voxel update solves a 2 × 2 system. It uses three Hessian diagonals, with the weights Λ(1−λ)2, Λλ(1−λ), and Λλ2.
  • With a frame_overlap_factor of 2, MACE4D puts each view into the proximal maps of two frames, and each of those frames treats the view as its own. In the new design, each view goes into the proximal map of one interval, and its hat weights divide it between the two frames.

7. Inputs, outputs, and logs

  • The labels are one uint8 volume with the shape of a frame. Label 0 is the background. The dict part_kinds maps every other label to 'static', 'part', or 'spring'. Each spring must touch exactly one static label and one part label. These two contacts give its fixed end and its moving end.
  • The result holds the frames as a float32 array of shape (K,) + recon_shape, and d as a float32 array of shape (K, M, 3) in voxels, where M is the number of moving parts. Row m of d belongs to the m-th part label in increasing order, and its three components follow the axis order of recon_shape. The result also holds a dict of run information.
  • With log_dir, the run writes the three log files of MACE4D and one more file, motion_log.csv. Each pass appends to all four files. The motion log has one row for each outer pass, with bt and the largest change of d.

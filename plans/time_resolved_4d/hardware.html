3. Hardware Mapping

This blueprint says what lives in host memory and in GPU memory, what each processor computes, and what moves between them, with sizes and times. Host memory limits the number of frames, and so the speed of motion that a run can follow.

1. Where things live

The frames live on the host, in the arrays of the MACE object, as in MACE4D. Each GPU keeps the data and the Hessian diagonals of the intervals assigned to it for the whole run. A task copies its frames from the host to a GPU, computes there, and copies its result back. Each GPU runs one task at a time.

2. Reference case

The sizes and times below use the scan of the MACE4D runs on gautschi, the 30 s Lilly phantom. Its frames are 260 × 260 × 728 voxels, which is 0.183 GiB each. Its sinogram is 2400 × 728 × 260, which is 1.69 GiB, with V=144 views per rotation over 16.7 rotations. The MACE4D reconstruction of this scan has 99 frames. The tables give three frame rates, F=6, 12, and 24 frames per rotation, which follow motion up to about 6, 12, and 24 voxels per rotation. The formulas in the second column hold for any scan.

One gautschi node has 1030 GB of host memory, which is 959 GiB. It therefore holds the reference case up to about F=24. Turning the warm starts off saves 2 × K frames. A dense motion field would add 3 × K frames, which is 220 GiB at F=24. The labels and d take 0.05 GiB instead.

An H100 has 80 GB, which is 74.5 GiB, so four H100s hold every column. A data-fit task adds about four frames to its GPU, and a temporal task adds about ten. Both are smaller than the denoiser slab in the reference case. When one frame exceeds denoise_slab_gb, a slab still holds one whole frame, so the denoiser needs about three frames on one GPU.

5. Work and time

ProcessorWhat it computesHow the work grows
each GPUthe two-frame VCD of its intervalsThe projection work does not depend on F, because each view is projected in one interval only. The work for each voxel grows with K.
any GPUthe denoiser slabs, the temporal pairs, and the registration between passesIt grows with K. The temporal tasks interpolate only in the moving parts and springs, because Mk is the identity on the static part.
hostthe consensus update, the folds of task outputs, the starting frames, and the stop testIt grows with K. Each MACE iteration copies 10 × K frames between the host and the GPUs, against 8 × K in MACE4D.

The times come from the MACE4D runs of the reference case on four H100s of one gautschi node with 56 host threads (plans/mace4d/experiments/m4d4_partition_advance.md). The right column is an estimate for F=6, not a measurement.

The run also needs the MACE4D reconstruction that gives the starting point. On the reference case, that reconstruction took about 18 minutes for its initial image and 24 to 27 minutes for ten iterations. The consensus update and the folds run on torch's host threads. With OMP_NUM_THREADS=1, the same MACE4D run took 2.6 times as long, so a run must leave torch its host threads.

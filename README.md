# mbirtorch_plans

Plans, surveys, findings, and experiment scripts for the
[mbirtorch](https://github.com/cabouman/mbirtorch) project (Bouman group, Purdue).
The documents here are the record of why the code is the way it is and what was measured.
The code itself, its docstrings, and its user documentation live in the mbirtorch repository.

New to the group's clusters?  Read [`.claude/cluster_use.md`](.claude/cluster_use.md) and
[`.claude/gpu-resources.md`](.claude/gpu-resources.md).  The collaboration style is in
[`.claude/claude_prompt.md`](.claude/claude_prompt.md), the writing style in
[`.claude/writing_style.md`](.claude/writing_style.md), and the engineering rules distilled
from past programs in [`.claude/lessons.md`](.claude/lessons.md).

## Layout

The top level says what kind of document a folder holds and where that document is in its life.

```
reference/   living documents, revised in place, never archived (the API specification,
             the geometry conventions)
surveys/     breadth: comparisons and gap lists, one folder per topic, revised as the
             field moves
plans/       depth: encapsulated tasks with increments, one folder per task
archive/     closed plans and programs, kept as records, scripts removed
decks/       slide decks
www/         the landing page of the group's report web root
tools/       scripts for the repository and the clusters, not experiments
```

Every plan and survey folder has the same shape:

```
plans/<task>/
  plan.md          the plan of record (surveys: survey.md), starting with the status header
  findings/        findings pages: records of what was measured, never rewritten
  experiments/     scripts and their records.  Every experiment has a companion .md, which may
                   cover several scripts and names them; modules, tests, and app files need none.
                   Small text results are committed under results/; large outputs are ignored.
  (other design documents, such as decisions.md, at the top level when a plan needs them)
```

## Rules

1. **The status header.**  `plan.md`, `survey.md`, and every reference document start with
   four lines: `Status`, `Updated`, `Code` (the mbirtorch branch and commits the work lives
   on), and `Next step` (one sentence).  Status is one of PROPOSED, APPROVED, ACTIVE, PAUSED
   (with the reason in the next step), COMPLETE, or SUPERSEDED.  Update the header at every
   review stop, then run `python tools/status_index.py`, which regenerates the tables below
   and lists any header older than a month.
2. **One plan of record per folder.**  A revision replaces `plan.md` in place; git keeps the
   earlier versions.  Superseded versions, dated snapshots, and session prompts are deleted
   when they stop being current.  A plan that a later plan replaces says so in its header.
3. **Findings are records.**  A findings page or a run record names the commit it measured
   and is not rewritten when the code moves on.
4. **Surveys feed plans.**  A survey's gap list marks each item as not planned, planned with
   a link to its plan folder, or done with a link.
5. **Archiving is one move.**  `git mv plans/<task> archive/<task>`, delete the scripts under
   `experiments/` (the `.md` records stay), and add a closing paragraph to `plan.md` that
   states the outcome and the commit at which the scripts were last present.  Sources of a
   deployed page, such as `plans/geometry_viewer/experiments/web/`, are not experiment scripts:
   they move to `tools/` with their build script instead of being deleted.
6. **Paths.**  Inside a document, a bare file name refers to a file in the same folder, and
   `findings/` and `experiments/` are relative to the plan folder; every other path is given
   from the root of this repository.  mbirtorch paths are given from the root of the
   mbirtorch repository; when such a path could also be read as a path in this repository, as
   `experiments/drunet/` can, the sentence or the document's paths paragraph names the
   repository.  Documents in `archive/` keep the paths of their time.
